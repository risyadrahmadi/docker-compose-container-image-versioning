# Docker Compose: Container Image Versioning

## Introduction

This project implements a **Build & Deploy process using CI/CD** with Docker Compose as the deployment platform.

Docker Compose is used to run multiple application components as containers on an STB server.

The Docker image build process is handled by GitLab CI/CD. Each source code release is assigned a Git tag as a version identifier. The Git tag is then used by the CI/CD pipeline to determine the Docker image version.

After the image is successfully built, it is pushed to the GitLab Container Registry. The deployment server then pulls the versioned image from the registry and runs it using Docker Compose.

This approach separates the image build process from the deployment process. The deployment server does not need to build the application image locally. It only needs access to the container registry and the Docker Compose deployment configuration.

---

## Objectives

The main objective of this project is to implement a Docker Compose deployment workflow using CI/CD and container image versioning.

The implementation covers the following objectives:

1. Build Docker images automatically using GitLab CI/CD.
2. Store Docker images in the GitLab Container Registry.
3. Use Git tags as Docker image version identifiers.
4. Deploy applications using Docker Compose.
5. Separate the build and deployment processes.
6. Ensure deployments use a specific image version.
7. Verify containers and application communication after deployment.

## Deployment Environment

Docker Compose is used on an STB server as the deployment host.

The deployment configuration is stored in:

```text
/opt/deploy-apps
```

The deployment directory can be accessed using:

```bash
cd /opt/deploy-apps
```

The directory can then be inspected using:

```bash
ls -lah
```

One of the Compose files used by the application is:

```text
docker-compose.apps.yml
```

The Compose file contains the application container configuration, images, networks, environment variables, ports, and other container settings.

## Application Components

The application consists of several components that communicate with each other through the Docker network.

The frontend is built using React JS and provides the application interface.

Requests from the frontend are forwarded to a Golang BFF (Backend-for-Frontend). The BFF communicates with the required backend components.

One backend component uses FrankenPHP and is identified as `kelas-01`. Another backend component uses Golang and is identified as `kelas-02`.

The application also uses MySQL and PostgreSQL databases according to the requirements of each component.

Docker Compose provides a centralized configuration for running these components.

## GitLab Runner

The Docker image build process is executed using a GitLab Runner configured with the **Docker executor**.

The runner uses a Docker-related tag so that the CI/CD job can be assigned to the appropriate runner.

The Docker executor allows GitLab CI/CD jobs to execute Docker commands inside a containerized environment.

The runner is also configured to communicate with the Docker daemon through the Docker socket:

```text
/var/run/docker.sock
```

This allows the CI/CD job to execute commands such as:

```bash
docker build
docker login
docker push
```

## GitLab Container Registry

The Docker image generated by the CI/CD pipeline is stored in the GitLab Container Registry.

The registry acts as the central storage location for the versioned Docker images.

The workflow separates the responsibilities between the build and deployment environments.

The GitLab Runner builds and pushes the image, while the deployment server pulls the image and runs it using Docker Compose.

This means the deployment server does not need the application source code to build the image.

It only needs:

* Docker
* Docker Compose
* Access to the GitLab Container Registry
* The deployment Compose configuration

---

## Login to GitLab Container Registry

Before pushing a Docker image, the CI/CD pipeline authenticates against the GitLab Container Registry.

The login process uses GitLab CI/CD variables:

```bash
echo "${CI_REGISTRY_PASSWORD}" | docker login "${CI_REGISTRY}" \
  -u "${CI_REGISTRY_USER}" \
  --password-stdin
```

The registry credentials are provided through CI/CD variables instead of being written directly into the source code.

The `--password-stdin` parameter allows the password to be provided through standard input.

This avoids putting the registry password directly into the command arguments.

## Image Versioning

Container image versioning is an important part of this implementation.

Instead of using `latest` as the primary image identifier, the application uses Git tags to create explicit image versions.

Example Git tags:

```text
v0.1.0
v0.1.1
v0.1.2
v0.1.3
...
v0.1.19
```

For example, when the application is released as:

```text
v0.1.19
```

the resulting Docker image can be identified as:

```text
registry.gitlab.com/docker-compose/franken-php:v0.1.19
```

The image naming convention is intentionally simple so that the relationship between the deployment platform, application, and version is easy to understand.

The same version can therefore be traced from the Git tag to the Docker image.

Previous image versions can also remain available in the registry and can be used when a specific version is required.

---

## Create a Git Tag

Git tags are used to identify the source code version that should be built and released.

After the source code changes are complete, create a Git tag:

```bash
git tag v0.1.19
```

Push the tag to GitLab:

```bash
git push origin v0.1.19
```

GitLab receives the tag and starts the CI/CD pipeline according to the repository's `.gitlab-ci.yml` configuration.

The Git tag is available inside the CI/CD pipeline through:

```text
CI_COMMIT_TAG
```

This allows the same version identifier to be used for both the source code release and the Docker image.

---

## Build Docker Image

During the build stage, the pipeline uses the Dockerfile available in the repository to create the Docker image.

The generic CI/CD command is:

```bash
docker build \
  -t "${CI_REGISTRY_IMAGE}:${CI_COMMIT_TAG}" .
```

`CI_REGISTRY_IMAGE` represents the image repository configured by GitLab, while `CI_COMMIT_TAG` contains the Git tag that triggered the pipeline.

For example, when:

```text
CI_COMMIT_TAG=v0.1.19
```

the resulting image can be represented as:

```text
registry.gitlab.com/docker-compose/franken-php:v0.1.19
```

The equivalent concrete Docker build command is:

```bash
docker build \
  -t "registry.gitlab.com/docker-compose/franken-php:v0.1.19" .
```

The version does not need to be manually entered into the CI/CD build command because it can be obtained from the Git tag.

---

## Push Docker Image

After the Docker image has been successfully built, it is pushed to the GitLab Container Registry.

The generic CI/CD command is:

```bash
docker push "${CI_REGISTRY_IMAGE}:${CI_COMMIT_TAG}"
```

For the example version used in this project:

```bash
docker push registry.gitlab.com/docker-compose/franken-php:v0.1.19
```

After the push is completed, the versioned image is available in the GitLab Container Registry.

The deployment server can then pull this image when performing the Docker Compose deployment.

---

## CI/CD Pipeline

The Docker Compose workflow consists of two main stages:

```yaml
stages:
  - build
  - deploy
```

The `build` stage is responsible for creating and pushing the Docker image.

The `deploy` stage is responsible for connecting to the deployment server and running Docker Compose.

During the build stage, the pipeline performs the following operations:

1. Authenticate to the GitLab Container Registry.
2. Build the Docker image.
3. Tag the image using the Git tag.
4. Push the image to the registry.

During the deployment stage, the pipeline connects to the deployment server using SSH.

The deployment process then enters the application directory and updates the running containers using Docker Compose.

Separating these stages makes the CI/CD process easier to understand and maintain.

---

## Deployment to STB

After the image has been pushed to the registry, the deployment process runs on the STB server.

The pipeline connects to the server using SSH and enters the deployment directory:

```bash
cd /opt/deploy-apps
```

The required image is pulled from the registry:

```bash
docker compose -f docker-compose.apps.yml pull
```

This command downloads the image version defined in the Compose configuration.

After the image has been updated, the application is started using:

```bash
docker compose -f docker-compose.apps.yml up -d
```

The `-d` option runs the containers in detached mode.

This allows the containers to continue running in the background after the deployment command finishes.

## Verify Containers

After deployment, the container status should be checked.

Use:

```bash
docker compose -f docker-compose.apps.yml ps
```

The running containers can also be checked with:

```bash
docker ps
```

The output can be used to verify whether the containers are running correctly.

Example application containers include:

```text
frontend
bff
deploy-apps-kelas-01-1
deploy-apps-kelas-02-1
kelas-03
nginx-kelas-00
```

A successful deployment should show the expected containers in a running state.

---

## Verify Docker Images

The Docker images available on the deployment server can be listed using:

```bash
docker images
```

This can be used to verify whether the expected image version has been downloaded.

For example:

```text
registry.gitlab.com/docker-compose/franken-php
```

The container configuration can also be inspected using:

```bash
docker inspect deploy-apps-kelas-01-1
```

The inspection output can be used to verify which image is actually being used by the container.

This is important because checking the container status alone does not confirm that the correct image version is running.

---

## Test Application Endpoint

After all containers are running, the application endpoint can be tested.

For example:

```bash
curl http://localhost/api/students
```

If the endpoint returns a valid application response, the backend application can be considered reachable.

Endpoint testing also helps verify that the Docker network, reverse proxy, and application routing are working correctly.

---

## Test Inter-Container Communication

Because the application consists of multiple containers, communication between containers should also be tested.

For example, communication from the BFF container to the `kelas-01` backend can be tested using:

```bash
docker exec bff wget -qO- --timeout=5 http://kelas-01/api/students
```

If the command returns a response from the backend, the BFF is able to communicate with the `kelas-01` container through the Docker network.

This test verifies that the containers are not only running individually but are also able to communicate according to the application architecture.

## Example Versioning Workflow

A typical release follows this sequence.

First, create a Git tag:

```bash
git tag v0.1.19
```

Push the tag:

```bash
git push origin v0.1.19
```

GitLab CI/CD receives the tag and builds the image.

The image is tagged as:

```text
registry.gitlab.com/docker-compose/franken-php:v0.1.19
```

The image is then pushed to the registry:

```bash
docker push registry.gitlab.com/docker-compose/franken-php:v0.1.19
```

The deployment server pulls the image:

```bash
docker compose -f docker-compose.apps.yml pull
```

Finally, Docker Compose starts the updated application:

```bash
docker compose -f docker-compose.apps.yml up -d
```

This creates a clear relationship between the Git version and the deployed container image.

## Security Considerations

This repository is intended to be public.

Registry credentials must not be stored in the repository.

Use GitLab CI/CD variables for sensitive values such as:

```text
CI_REGISTRY_USER
CI_REGISTRY_PASSWORD
```

Private server IP addresses, SSH private keys, passwords, access tokens, and other credentials should also be excluded from the repository.

The image names shown in this documentation are examples intended to demonstrate the versioning pattern.

## Result

The Docker Compose implementation successfully establishes a CI/CD-based Build & Deploy workflow.

The source code is versioned using Git tags, and the same version identifier is applied to the Docker image.

For example:

```text
Git Tag
v0.1.19
```

becomes:

```text
registry.gitlab.com/docker-compose/franken-php:v0.1.19
```

The image is then stored in the GitLab Container Registry and pulled by the deployment server.

Docker Compose is used to start the application containers using the versioned image.

The deployment is verified through container status checks, image inspection, application endpoint testing, and inter-container communication testing.

---

## Conclusion

This project demonstrates how Docker Compose can be integrated with GitLab CI/CD to implement versioned container image deployment.

Git tags provide a clear version identifier for application releases. The same identifier is used for the Docker image, making it easier to determine which application version is being deployed.

GitLab Runner handles the image build and push process, while the deployment server pulls the required image from the GitLab Container Registry and runs it using Docker Compose.

Using explicit image versions instead of relying on `latest` provides better traceability and makes it easier to identify the version currently deployed.

This Docker Compose implementation also provides the foundation for the next deployment stages using **K3s** and **ArgoCD/GitOps**.
